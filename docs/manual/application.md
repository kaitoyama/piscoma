# ISUCOMA アプリケーションマニュアル

本書は ISUCOMA（イスコマ）の参加者向けアプリケーションマニュアルである。サービスの概要・用語・
ドメインルール・API 外部仕様を説明する。当日の競技ルール（スコア・fail 条件・レギュレーション）は
[当日マニュアル](./rules.md) を参照すること。

## 1. サービス概要

ISUCOMAは椅子専門のライブコマースサービスである。セラー（配信者）がライブ配信で椅子・椅子グッズを
紹介し、視聴者はコメントで盛り上がりながらその場で商品を購入する。配信中、セラーは不定期に限定数量の
目玉商品を「ドロップ」し、視聴者が一斉に購入に殺到する。

競技の題材はこのサービスのバックエンド API である（映像配信そのものは題材外）。負荷走行中に成立した
注文の合計金額（GMV）を基本としたスコアで競う。

## 2. 用語

| 用語 | 定義 |
|---|---|
| 配信（Live） | セラーが行うライブ配信。負荷走行中は常に配信中であり、開始・終了の概念はない |
| 棚（Shelf） | 配信に紐づく販売中商品の一覧 |
| 通常商品 | 常時棚に並ぶ商品。単価は1,000〜5,000 ISU |
| ドロップ（Drop） | 配信中に予告つきで販売される限定数量・高単価の目玉商品。単価は20,000〜100,000 ISU |
| カート（Cart） | 在庫を一時的に引き当てた状態。有効期限（TTL）付き |
| チェックアウト | カートに対する決済確定。外部決済ゲートウェイ（モック）を呼び出す |
| GMV | チェックアウトが成立した注文の合計金額（価格−割引額の総和）。スコアの基本 |
| 購入速報 | 「〇〇さんが△△を購入しました」を配信内の全視聴者に届けるフィード |
| アイコン | 視聴者・セラーのアバター画像。コメントと購入速報に表示される |
| ピン留め | セラーが「今紹介中の商品」として配信画面に固定表示する商品 |
| クーポン | セラーが配信中に発行するライブ限定・先着制の割引券。チェックアウト時に適用する |
| いいね | 視聴者が配信に送るリアクション（ハート連打） |
| セール強度 | 参加者（競技者）が設定できる全体キャンペーンレベル（1〜4） |
| 視聴者数 | 配信に直近アクセスした視聴者のユニークユーザー数（詳細は4.9節） |
| Idempotency-Key | チェックアウトのリトライ安全性のためにクライアントが発行する一意な冪等キー |

## 3. ユーザーと行動の概観

サービスには3種類のロールが存在する。ロールはアカウントに紐づき、ログイン後のセッションで判別される。

### 3.1 視聴者（Viewer）

各視聴者は4種類の嗜好カテゴリ（`gaming` / `zaisu` / `office` / `outdoor`）のいずれか1つを持つ。
アカウント登録時に指定する。視聴者は以下のような行動を取る。

- ホームフィードから配信を選んで入室する
- 配信中、コメント一覧・棚（商品一覧）・通知をポーリングして視聴を続ける
- コメントを投稿する。自分のコメントにセラーが返信することがある
- 配信の盛り上がりに応じて「いいね」を送信する
- ピン留め商品の切替やドロップ予告など、配信内で起きる出来事を通知で受け取る
- クーポン発行の通知を受けてクーポンの先着取得を試みる
- 通常商品をカートに投入し、期限内にチェックアウトして購入する
- ドロップ開始の通知を受けて目玉商品のカート投入を試みる
- 購入速報を受信して、同じ商品を追随して購入することがある

### 3.2 セラー（Seller）

配信を主催し、以下のような行動を取る。

- 自分の売上サマリを確認する
- 通常商品の在庫を追加投入する
- ドロップ（在庫数・単価・予告時刻を指定した限定商品）を企画・登録する
- クーポン（固定額引き・先着枚数・配信限定）を発行する
- ピン留め商品を定期的に切り替える
- 新着コメントに返信する（視聴者向けと同一のコメント投稿APIを、返信先ID付きで使う）
- 商品の追加・編集を行う

### 3.3 運営（Admin）

サービス運営者として以下を行う。

- セラーの売上ランキングを確認する
- カテゴリ・価格帯を横断した商品検索を行う
- セール強度（1〜4）を設定する

## 4. ドメインルール

### 4.1 商品と在庫

在庫は商品ごとに単一の数値で管理される。カートに投入した時点で在庫が1引き当てられ、その引き当ては
カートの有効期限まで保持される。1回のカート投入は1商品1点固定であり、同一ユーザーが同一商品の
有効なカートを同時に2つ以上持つことはできない。

### 4.2 カートと有効期限（TTL）

カート投入が成功すると、レスポンスに `cart_id` / `expires_at` / `remaining_ms` が含まれる。

- カートの TTL（有効期限）は **60秒** である
- 有効期限内のカートのみチェックアウトが成立する。有効期限を過ぎたカートへのチェックアウトは
  4xx で失敗する（正しい仕様上の挙動である）
- 有効期限を過ぎたカートの在庫は解放され、他の視聴者が購入できるようになる
- 有効期限が切れてから在庫が再購入可能になるまでの猶予は **5秒以内** である
- 有効期限内のカートの在庫を解放すること、および有効期限内のチェックアウトを拒否することは
  いずれもサービスの整合性に反する

### 4.3 カウントダウンとクライアント挙動の仕様

カート状態取得API（`GET /api/carts/:id`）は `remaining_ms`（残りミリ秒）を返す。この値だけを
返すレスポンスに対して、クライアントは毎秒ポーリングして残り時間を表示する。

**レスポンスに `expires_at`（絶対時刻）が含まれる場合、クライアントはこれをもとにローカルで
残り時間を計算し、以後のポーリングを行わない。**

同様に、通知取得APIのレスポンスには `retry_after_ms`（次回ポーリングまでの間隔）と `jitter_ms`
（間隔に対する揺らぎ幅）が含まれる。クライアントは次回のポーリングまで `retry_after_ms ± jitter_ms`
の範囲でランダムに選んだ間隔を空ける。

### 4.4 ドロップ

ドロップはセラーが企画する限定数量・高単価の目玉商品であり、以下のライフサイクルを持つ。

```
scheduled（予告） → active（販売中） → sold_out（売り切れ） または closed（終了）
```

- ドロップ登録時には販売開始時刻（`starts_at`）を指定する。現在時刻から15秒以上先でなければ登録できない
- 開始15秒前になると、予告が通知として全入室者に配信される（`drop_scheduled`）
- 開始時刻になると `drop_started` が配信され、`status` が `active` になる
- 販売期間（`starts_at` 〜 `ends_at`）外のカート投入は 409 で拒否される
- 在庫が尽きると `sold_out`、販売終了時刻を過ぎると `closed` に遷移する
- ドロップ販売期間中に有効期限切れで在庫が解放された場合、その在庫はドロップ期間内であれば
  再び購入可能になる

### 4.5 チェックアウトと決済

チェックアウトは外部決済ゲートウェイ（ベンチマーカー同梱の決済モック）を呼び出して確定する。
決済モックはリクエストごとに約30msの固定レイテンシを持ち、一定割合のリクエストを一時的に失敗
（503）させる。この一時失敗に対するリトライには冪等キーが必要である。

**チェックアウトAPIの非同期化は許容される。** 同期でチェックアウトの結果を確定させて返す実装に
代えて、受付（202相当のレスポンス）のみを返し、結果を通知経由で伝える実装を用いてもよい。この場合、
以下の2点を満たさなければならない。

1. 受付から結果が確定するまでは **2秒以内** であること
2. 同一商品に対する在庫確保の順序は、カート投入を受け付けた順序（FIFO）を維持すること

### 4.5.1 Idempotency-Key（チェックアウトの冪等性）

`POST /api/carts/:id/checkout` はリクエストヘッダ **`Idempotency-Key`**（クライアントが発行する一意な
文字列。カートごとに1つ発行することを想定）を送信しなければならない。このヘッダを付けずに呼び出した
場合は `400` が返る。

チェックアウトはネットワーク不調時のクライアントの再送に対して安全でなければならない。参考にした
Stripe の冪等キー設計に準じ、セマンティクスを次の表に整理する。

| ケース | 期待される挙動 | 分類 |
|---|---|---|
| 同一キーから異なる成功注文が2つ生まれる | 起きてはならない | 整合性違反 |
| 再生する場合に初回と異なる内容を返す | 起きてはならない | 整合性違反 |
| 同一キーのリクエストが処理中に重複して届く | `409` で拒否する、または処理完了を待ち合わせて同一結果を返す。どちらも仕様上正しい挙動 | 正しい4xx（減点なし） |
| 完了済みキーへの再送 | 初回と同一の結果を再生し `Idempotency-Replayed: true` ヘッダを付けることが望ましい（**推奨**。必須ではない） | SHOULD |
| 完了済みキーへの再送に対し再生せず4xxを返す | 許容される仕様上の挙動だが、クライアントが「決済結果が分からず不安になり、注文履歴を確認しに行く」といった追加の挙動を誘発しうる | 正しい4xx（減点なし）だが体験は劣る |
| 同一キーで異なるカート・クーポンを指定した再送（キーの使い回し） | `4xx` で拒否する | 正しい4xx（減点なし） |

決済ゲートウェイ（モック）への冪等キーはサーバー内部で管理されるものであり、上記のクライアント発行の
`Idempotency-Key` とは別レイヤーである。同一カートの着金がちょうど1件であるべき、という既存の要件は
不変である。

### 4.6 通知

ドロップの予告・開始、ピン留め切替、クーポン発行、チェックアウト結果などのイベントは通知エンドポイント
（`GET /api/lives/:id/notifications`）経由で配送される。通知はブロードキャスト通知（配信内の全視聴者
向け）と個人宛て通知（自分のチェックアウト結果など）に分かれ、`since_id` を指定することで前回取得
以降の新着分のみを取得できる。

**通知のJSONポーリングをServer-Sent Events（SSE）による配信に置き換えることは許容される。** どちらの
配送方式でも、イベントの発生からクライアントへの到達までは3秒以内であることが期待される。

**ベンチマーカーはSSEを実際に読む。** 通知取得リクエストには常に `Accept: text/event-stream` が
付与される。サーバーがこれを無視してJSONを返す場合は従来どおりのポーリングで動作するが、
`Content-Type: text/event-stream` で応答した場合、ベンチマーカーはストリーミング受信に切り替え、
以後そのクライアントの通知ポーリングは発生しなくなる。SSEで配信する場合のイベント形式は次のとおりである。

- 各イベントは `id:` 行に通知ID、`data:` 行にJSONポーリング版と同一形式の通知1件（`id` / `type` /
  `payload` / `created_at`）を含む
- クライアントが切断後に再接続する際は `Last-Event-ID` ヘッダを送信できる。このヘッダはクエリパラメータ
  `since_id` と同義に扱われ、それより大きいIDの通知から配信が再開される
- 配信対象（ブロードキャスト通知・本人宛て通知の区別）や到達3秒以内の期待は、ポーリングとSSEのどちらでも
  同じである

### 4.7 商品ピン留め（今紹介中の商品）

各配信は同時に1つのピン留め商品（`pinned_product_id`）を持つ。セラーが
`PUT /api/seller/lives/:id/pin` で切り替えると、切替は通知として配信内の全視聴者に配送される
（3秒以内の到達が期待される）。配信詳細（`GET /api/lives/:id`）にも常に現在のピン留め商品が
含まれ、通知の内容と配信詳細の内容は一致していなければならない。

ピン留め商品には視聴者の注目が集まりやすく、切替のたびにその商品の閲覧・購入が集中する傾向がある。

### 4.8 ライブ限定クーポン

セラーは配信単位でクーポンを発行できる（`POST /api/seller/coupons`）。クーポンの規則は次のとおりである。

- **固定額引き**: 発行時に指定した金額（ISU）を割り引く
- **先着制**: 発行時に指定した枚数（`total_count`）まで、先着順に取得できる
- **1人1枚**: 同一ユーザーが同一クーポンを複数回取得することはできない
- **配信限定**: 発行元の配信に属する商品にのみ適用できる

視聴者はクーポン発行の通知を受けて `POST /api/coupons/:id/claim` で取得を試みる。取得したクーポンは
チェックアウト時に `coupon_id` を指定して適用する。割引額は `min(商品価格, クーポンの額面)` であり、
支払額（GMVへの計上額）は `商品価格 − 割引額` となる。

### 4.9 いいね（リアクション）

視聴者は配信に対して「いいね」を送信できる（`POST /api/lives/:id/reaction`）。同一ユーザーの連続送信に
制限はない。配信の統計（いいね数）は配信詳細・フィードに表示され、盛り上がっている配信ほど視聴者の
滞在・購入意欲・入室選好が上がる傾向がある。

配信統計（視聴者数・いいね数）・売上サマリ・ランキング・購入速報の残り在庫表示など、集計値の表示には
**鮮度許容2秒**が適用される。取得後2秒以内のキャッシュされた値を表示することは許容される。

**視聴者数の定義**: `stats.viewer_count` は、その配信の視聴者向けエンドポイント（配信詳細・コメント
一覧・棚）へ**直近30秒以内にアクセスしたユニークユーザー数**である。参加者はこの定義に沿って
視聴者の在室状態を管理する実装を選んでよい（例: アクセスのたびに最終アクセス時刻を記録するテーブルを
用いる、等）。

### 4.10 購入速報（ソーシャルプルーフ）

チェックアウトが成立すると、その配信の全視聴者に「購入者の表示名＋商品名＋アイコン」を含む購入速報が
配送される（`GET /api/lives/:id/purchases`）。速報には対象商品の残り在庫数（`remaining_stock`）も
含まれる。速報は成立から3秒以内に到達することが期待される。

速報に表示されるのは表示名のみであり、メールアドレス等の個人情報を含めてはならない。また、実在しない
購入の速報を配信することはサービスの整合性に反する。

### 4.11 画像配信（商品画像・アイコン）

商品画像（`GET /api/products/:id/image`）とユーザーアイコン（`GET /api/users/:id/icon`）は
`image/png` で配信される。ユーザーアイコンは自分自身のみ更新でき（`POST /api/icon`）、更新後の
取得は直ちに新しい画像を返さなければならない。

**クライアントはリクエストヘッダに `If-None-Match` を送信する。** レスポンスの内容（バイト列）の
ハッシュ値に基づいて正しく `304 Not Modified` を返した場合、画像本体の転送は発生しない。画像の内容
ハッシュが実際の内容と一致しないレスポンス（更新後に古い画像を返す等）はサービスの整合性に反する。

### 4.12 セール強度

セール強度は `POST /api/admin/campaign` でレベル1〜4を設定できる（Adminロールのみ）。競技中いつでも
変更できるが、負荷走行に適用されるのは負荷走行開始時点（`POST /api/initialize` 実行時点）の値である。
`POST /api/initialize` のレスポンスに含まれる `campaign` フィールドで、その走行に採用された値を
確認できる。

セール強度を上げるとドロップの頻度・在庫量や視聴者の流入が増え、獲得できるGMVの機会が増える。
一方でリクエストの並列度・急峻さも増すため、自サーバーの処理能力に見合わないレベルを選ぶとエラーが
増加し、かえってスコアを落とす場合がある。

### 4.13 クライアント（ベンチマーカー）の挙動に関する参考情報

以下はベンチマーカーが模擬する仮想クライアントの挙動のうち、実装方針の判断材料として開示する事実である。
具体的な閾値・発生確率は開示しない。

- **応答が遅いとクライアントはページを再読み込みする。** 配信への入室・閲覧が一定時間内に完了しない、
  またはタイムアウトした場合、クライアントは表示に必要な一式のリクエストを再度送信する。これを一定回数
  繰り返しても完了しなければ、そのクライアントは閲覧を諦めて配信から離脱する
- **決済応答が遅いとクライアントは再送する。** チェックアウトの応答が遅い、またはタイムアウトした場合、
  クライアントは同一の `Idempotency-Key` で再送する。応答前に重ねて送信する（連打）こともある。
  再送してもチェックアウトの結果が判然としない場合、クライアントは `GET /api/orders` で自分の注文履歴を
  確認しに行くことがある
- これらの挙動自体は減点対象ではないが、遅延に応じて発生するリクエスト量が増えるため、レイテンシの
  改善は見かけ上の負荷そのものを減らす効果を持つ

## 5. APIリファレンス

以下は全30エンドポイントの一覧である。特記のない `error` フィールドはすべて `{"error": "<メッセージ>"}`
形式の文字列である。日時はRFC3339形式の文字列で表現される。カート投入レスポンスの `expires_at` と
ドロップ登録レスポンスの `starts_at`/`ends_at` はミリ秒精度で固定表現される（例:
`2026-07-02T12:00:00.000+09:00`）。それ以外の `created_at` 等はミリ秒精度を保証しない
（秒未満が0の場合は省略されることがある）。

### 5.1 共通

#### `POST /api/initialize`
データベースを初期データの状態にリセットする。負荷走行のたびにベンチマーカーが最初に呼び出す。

- 認証: 不要
- リクエスト: なし
- レスポンス: `200`
  ```json
  {"lang": "go", "campaign": 1}
  ```
- 主なステータスコード: `200`

#### `POST /api/register`
視聴者アカウントを新規作成し、そのままログイン済みセッションを発行する。

- 認証: 不要
- リクエスト:
  ```json
  {"display_name": "string", "email": "string", "password": "string", "preference_category": "gaming|zaisu|office|outdoor"}
  ```
- レスポンス: `201`
  ```json
  {"id": 1, "email": "string", "display_name": "string", "role": "viewer", "preference_category": "gaming", "created_at": "..."}
  ```
- 主なステータスコード: `201`, `400`（必須項目欠如・不正な嗜好カテゴリ）, `409`（メールアドレス重複）

#### `POST /api/login`
視聴者・セラー・Adminの3ロール共用ログイン。ロールはアカウントに紐づく。

- 認証: 不要
- リクエスト:

- 主なステータスコード: `200`, `400`, `401`（資格情報不一致）

### 5.2 視聴者向け

#### `GET /api/feed`
おすすめ配信の一覧を取得する。

- 認証: 必要（ロール不問）
- リクエスト: なし
- レスポンス: `200`
  ```json
  [{"id": 1, "title": "string", "category": "gaming",
    "seller": {"id": 1, "display_name": "string"},
    "stats": {"viewer_count": 0, "reaction_count": 0},
    "products": [{"id": 1, "name": "string", "price": 3000, "remaining_stock": 10}]}]
  ```
  `products`（各配信の棚の要約。`GET /api/lives/:id/products` が返す商品のうち
  `id`・`name`・`price`・`remaining_stock` のみを持つ）は**含めても省略してもよい**。含める場合、
  `remaining_stock` は鮮度許容2秒の対象になる。クライアントは `products` が含まれていればそれを
  その配信の棚として扱い、省略されていれば入室時に別途 `GET /api/lives/:id/products` を呼び出す。
- 主なステータスコード: `200`, `401`

#### `POST /api/lives/:id/comments`

#### `GET /api/lives/:id/notifications`
配信のブロードキャスト通知と自分宛て通知を `id` 昇順で取得する。

- 認証: 必要
- クエリパラメータ: `since_id`（省略時0。これより大きい `id` の通知のみを返す）
- リクエストヘッダ: `Accept: text/event-stream`（任意）を送信できる。`Last-Event-ID`（任意）は
  `since_id` と同義に扱われる
- リクエスト: なし
- レスポンス（JSON、`Accept` が `text/event-stream` を含まない、またはサーバーが未対応の場合）: `200`
  ```json
  {"notifications": [{"id": 1, "type": "drop_scheduled", "payload": {}, "created_at": "..."}],
   "retry_after_ms": 500, "jitter_ms": 0}
  ```
- レスポンス（SSE、サーバーが対応している場合。`Content-Type: text/event-stream`）: 4.6節参照。
  イベントごとに `id:`（通知ID）と `data:`（JSON版と同一形式の通知1件）を送出する
- 主なステータスコード: `200`, `400`（`since_id` が不正）, `401`, `404`

  ```json
  {"cart_id": 1, "product_id": 1, "remaining_ms": 42000, "status": "active"}
  ```

- 認証: 必要
- リクエスト: なし
- レスポンス: `204`（本文なし）
- 主なステータスコード: `204`, `401`, `404`

#### `POST /api/carts/:id/checkout`
カートに対して決済を実行し、注文を確定する。

- 認証: 必要
- リクエストヘッダ: `Idempotency-Key`（**必須**。クライアント発行の一意な文字列。4.5.1節のセマンティクス
  に従う）
- リクエスト:
  ```json
  {"coupon_id": null}
  ```
- レスポンス: `200`
  ```json
  {"order_id": 1, "product_id": 1, "price": 3000, "discount": 500, "total": 2500}
  ```
  完了済みキーへの再送を再生する場合、レスポンスヘッダに `Idempotency-Replayed: true` を付けることが
  望ましい（SHOULD。4.5.1節参照）。
- 主なステータスコード: `200`, `400`（`Idempotency-Key` ヘッダなし・クーポンが未取得・使用済み・対象外の配信）,
  `401`, `404`（カートが存在しない・他人のカート・既にチェックアウト済み）,
  `409`（クーポンの二重使用が競合した場合・同一 `Idempotency-Key` が処理中または他のカート/クーポンを
  指して使い回された場合）, `410`（カートの有効期限切れ）,
  `502`（決済が成立しなかった場合。カートは`active`のまま残る）

#### `GET /api/seller/sales`

  ```json
  {"total_gmv": 12000, "order_count": 4,
   "by_product": [{"product_id": 1, "name": "string", "sold_count": 2, "gmv": 6000}]}
  ```

- 主なステータスコード: `200`, `401`, `403`

#### `POST /api/seller/products`
自分の配信に商品と在庫を追加する。

- リクエスト:
  ```json
  {"live_id": 1, "name": "string", "description": "string", "category": "gaming", "price": 3000, "quantity": 10}
  ```
- レスポンス: `201`
  ```json
  {"product_id": 1}
  ```
- 主なステータスコード: `201`, `400`, `401`, `403`（他セラーの配信を指定）, `404`

#### `PUT /api/seller/products/:id`
自分の商品の名称・説明・価格の変更、在庫の追加投入を行う。フィールドはすべて省略可能。

- リクエスト:
  ```json
  {"name": null, "description": null, "price": null, "add_quantity": 10}
  ```
- レスポンス: `200`
  ```json
  {"product_id": 1}
  ```
- 主なステータスコード: `200`, `400`（`add_quantity` が正の整数でない）, `401`, `403`（seller以外のロール）, `404`（自分の商品以外）

#### `POST /api/seller/drops`
自分の配信にドロップ（予告時刻・在庫・単価を指定した限定商品）を登録する。

- リクエスト:
  ```json
  {"live_id": 1, "name": "string", "description": "string", "category": "gaming",
   "price": 30000, "quantity": 5, "starts_at": "...", "duration_seconds": 60}
  ```
  `duration_seconds` は省略時60秒（10〜600の範囲）。`starts_at` は現在時刻より15秒以上先でなければならない。
- レスポンス: `201`
  ```json
  {"drop_id": 1, "product_id": 1, "starts_at": "...", "ends_at": "..."}
  ```
- 主なステータスコード: `201`, `400`（予告リード不足・不正な値）, `401`, `403`, `404`

#### `PUT /api/seller/lives/:id/pin`
自分の配信のピン留め商品を切り替える。

- リクエスト:
  ```json
  {"product_id": 1}
  ```
- レスポンス: `200`
  ```json
  {"product_id": 1, "name": "string", "price": 3000}
  ```
- 主なステータスコード: `200`, `400`（指定商品がその配信に属さない）, `401`, `403`（他セラーの配信）, `404`

#### `POST /api/seller/coupons`
自分の配信にクーポンを発行する。

- リクエスト:
  ```json

  ```
- レスポンス: `201`
  ```json
  {"coupon_id": 1}
  ```
- 主なステータスコード: `201`, `400`（`amount`/`total_count` が0以下）, `401`, `403`, `404`

- 主なステータスコード: `200`
