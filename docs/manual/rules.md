# ISUCOMA 当日マニュアル

本書は ISUCOMA（イスコマ）競技当日の競技ルールを説明する。サービスの仕様・API リファレンスは
[アプリケーションマニュアル](./application.md) を参照すること。

## 1. 競技形式

参加者は配布されたリファレンス実装（Go）を自由に改変し、ベンチマーカーによる負荷走行でスコアを
競う。ベンチマーカーは対象環境に対して `POST /api/initialize` によるデータリセットから開始し、
一定時間の負荷走行（load）を行った後、走行結果の整合性検証（validation）を行ってスコアを算出する。

| 項目 | 内容 |
|---|---|
| 予選・本選日程 | （当日案内のとおり） |
| 計測回数・最終計測の扱い | （当日案内のとおり） |
| 競技時間 | （当日案内のとおり） |

## 2. スコア

```
スコア = GMV − 1,000 ISU × エラー数
```

- **GMV**: 負荷走行中に成立した注文の合計金額（商品価格 − クーポン割引額の総和）
- **エラー数**: 5xxレスポンス・仕様上正しくない4xxレスポンス・タイムアウトの合計件数
- スコアの下限は0とする（計算結果が負になった場合は0として報告される）

### 2.1 タイムアウトとエラーの扱い

1リクエストあたりのタイムアウトは1秒とする。1秒以内にレスポンスが得られなかったリクエストは
エラーとして扱われる。

### 2.2 正しい4xxは減点されない

アプリケーションマニュアルに記載された、仕様上正しい4xxレスポンス（例: 売り切れの409、カート有効期限
切れチェックアウトの410、クーポン残枚数0や二重取得の409、`Idempotency-Key` なしの400・処理中/使い回し
の409など）はエラー数に含まれない。参加者はこれらのレスポンスを仕様どおりに返し続ける必要がある。

## 3. fail条件（スコア0）

以下のいずれかに該当した場合、その走行のスコアは0として報告される。

- 商品の初期在庫と追加投入分の合計を超えて販売が成立すること（オーバーセル）
- カートの有効期限が切れる前に在庫が解放されること、または有効期限内のチェックアウトが拒否されること
- GMVと決済ゲートウェイの着金記録が一致しないこと
- 同一商品への在庫確保順序が、カート投入を受け付けた順序（FIFO）と異なること
- 実在しない購入の速報が配信されること、同一の購入速報が重複して配信されること、
  購入速報の並び順が新しい順になっていないこと
- クーポンが発行枚数を超えて配布されること、同一ユーザーに二重配布されること、同一クーポンが
  二重に使用されること、対象外の配信の商品に適用されること、割引額の計算を誤ること
- 同一の `Idempotency-Key` から異なる成功注文が2つ生まれること、または完了済みキーへの再送を
  再生する際に初回と異なる内容を返すこと
- 配信のいいね数の表示が、鮮度許容2秒の範囲を超えて実際の値から乖離すること
- ピン留め商品の通知内容と配信詳細のピン留め商品が一致しないこと
- 購入速報・コメント等のレスポンスに表示名以外の個人情報（メールアドレス等）が含まれること
- 他ユーザーの注文・カート・コメントなどが漏洩すること
- エラー率が全リクエストの5%を超えること
- `POST /api/initialize` が30秒以内に完了しないこと

## 4. セール強度

`POST /api/admin/campaign` でレベル1〜4を設定できる。競技中いつでも変更できるが、負荷走行に
適用されるのは走行開始時点（`POST /api/initialize` 実行時点）の値である。`POST /api/initialize`
のレスポンスの `campaign` フィールドで、その走行に採用された値を確認できる。

セール強度を上げるとドロップの頻度・在庫量や視聴者の流入が増え、獲得できるGMVの機会が増える。
一方でリクエストの並列度・急峻さも増すため、自サーバーの処理能力に見合わないレベルを選ぶと
エラーが増加し、かえってスコアを落とす場合がある。計測前に自サーバーの処理能力を見極めた上で
レベルを選ぶこと。

## 5. ベンチマーカーの実行方法

ベンチマーカーは `bench/` に配置されている。対象環境（`provisioning/compose.yaml` で起動した
`http://localhost`）に対して、手元での動作確認に利用できる。

```bash
# 1. 対象環境を起動しておく
cd provisioning && docker compose up --build -d

# 2. ベンチを実行する
cd bench
go run . -target http://localhost -payment-url http://localhost:5000

# 短時間・少人数での動作確認
go run . -duration 30s -viewers 5
```

実行すると prepare（`POST /api/initialize` の30秒制限チェック・初期データとの整合性チェック）→
load（負荷走行）→ validation（整合性検証）の順に進み、最後にGMV・リクエスト成功/失敗数・
fail判定とその理由が標準出力に報告される（`RESULT: PASS` / `RESULT: FAIL`。fail時は終了コード1）。

主なCLIフラグ:

| フラグ | 説明 |
|---|---|
| `-target` | ISUCOMA webapp のベースURL（デフォルト `http://localhost`） |
| `-payment-url` | 決済モックのベースURL（デフォルト `http://localhost:5000`） |
| `-duration` | 負荷走行時間（デフォルト180秒） |
| `-viewers` | 負荷走行の並列視聴者数（省略時はセール強度に応じた既定値を使用） |

## 6. レギュレーション

- ベンチマーカー（`bench/`）・決済モック（`payment-mock/`）・初期データ生成物
  （`webapp/sql/init/seed.sql` 等）の改変は禁止する
- リファレンス実装のAPIレスポンス形式（フィールド名・型・意味）は、アプリケーションマニュアルおよび
  [APIリファレンス](./application.md#5-apiリファレンス) に記載された仕様と互換性を保つ範囲で変更すること。
  ベンチマーカーが解釈できないレスポンスは、対応するリクエストのエラーとして扱われる
- 実装言語・フレームワーク・ミドルウェア構成の変更は自由とする
- 上記に反する行為が確認された場合、当該計測は無効とする
